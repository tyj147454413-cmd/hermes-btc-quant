# Hermes BTC 自我学习系统架构设计（v1.0）

> **版本**：2026-08-21 首版（round35 随附）
> **地位**：学习系统的架构合约。任何偏离本文档的"学习"行为（自动改表、自动改权重、绕过反事实落规则）均违规。
> **由来**：三轮 AI 意见审查融合（审查记录：`data/hermes_model_library_review_20260821.md`）。本文档剔除的四个错误主张：教训直落 G5 硬规则（n=0 行为改变）、calibrate_probability.py 出四维表（实为二维）、"P&L 回测前置"（仅 confidence 纯日志前提下是伪命题，见 §10）、校验层 last-check 药方（时间线证明无效，见 §7）。

## 1. 背景：现状与缺口

**已有资产**：
- 数据飞轮：`data/snapshots/`（每场快照）+ `data/hermes_results.jsonl`（已结算，399 条，日均 19 场）+ `BTC_1H_Trade_Journal/`（复盘笔记）+ `data/review-lessons.json`（结构化对/错因子）
- 统计工具：`scripts/factor_attribution.py`（逐因子判别力）、`scripts/calibrate_probability.py`（二维概率校准）、`scripts/regime_split_replay.py`（四维拆分 + 漂移告警，本文档 §8 的执行器）
- 反事实回测模式：round18/20/22/23/25 先例（replay 条件 → 全库重放 → 翻对/翻错/误伤量化 → 用户决策）
- 规则权威链：`prompt_exec.md` + `rule_engine.py` + selftest + SYNC_MAP 同步铁律

**缺口（本系统要补的）**：
1. 四维胜率表是 round30 的 118 场静态快照，无定期重算机制 → §8 校准工具 + 触发条件
2. 教训只在 markdown 里"躺着"，无结构化排队与验证管道 → §6 候选规则 schema
3. 无建议生成与提案分层规范 → §9 阶段 3
4. 时序层流程（last-check/refresh）无审计 → §3 监控环

## 2. 核心概念：三层混合体 + 监控环

本系统的"模型"不是单一 ML 模型，是**三层风险等级不同的学习机制 + 一个监控环**。分层由数据量决定（210 场引擎可复算样本：统计层够、权重层勉强、结构层远不够——momentum_health 46.7% 偏反被回测否决是直接证据）：

| 层 | 是什么 | 学习方式 | 验证门槛 | 风险 |
|---|---|---|---|---|
| **统计层** | 四维胜率表（`rule_engine._probability`） | **可自动**（纯查表映射） | n≥30 格可直接落；n<30 告警不落 | 低（confidence 纯日志，见 §10） |
| **权重层** | 评分表 ×1/×2 因子权重 | **半自动**（提议→回测→人工批准） | 30+ 样本 + 反事实净效果>0 | 中（一个因子影响所有场） |
| **结构层** | G1-G6 门槛/H 规则/翻向逻辑 | **仅人工**（教训→回测→拍板） | ≥3 个反事实场景 + 用户决策 | 高（round31.1 移除翻向级决策） |
| **监控环** | last-check/refresh/校验流程 | 不学习，只审计 | 见 §3 | 时序 bug 不在任何学习层内 |

**为什么监控环不是"第五学习层"**：前三层"从数据学参数"，监控环"对流程做工程审计"（last-check 触发率、refresh 率、v1/v2 标记分布）——它没有可学习参数，混进分层表会糊掉设计边界。二者**并列**于同一闭环。

## 3. 闭环架构

```
┌──────────────────────── 学习环 ────────────────────────┐
│                                                        │
│  交易(每小时) → 结算 → 复盘+教训 → ① 统计重算(regime_split_replay, │
│  触发=新增≥50场已结算或每周日先到)                        │
│                    ↓                                   │
│  ② 候选规则队列(candidate_patches.json, §6 schema)      │
│                    ↓                                   │
│  ③ 建议生成器(阶段3, LLM周度/事件触发, 提案必附回测命令)  │
│                    ↓                                   │
│  ④ 反事实回测(全库重放, 行为改变数/翻对/翻错/误伤量化)    │
│                    ↓                                   │
│  ⑤ 用户拍板 → ⑥ SYNC_MAP全链落地+锚点抬升+selftest       │
│                    ↓                                   │
│  ⑦ 30场监控窗 → 恶化则回滚(§11) → 回到交易               │
└────────────────────────────────────────────────────────┘
┌──────────────────────── 监控环 ────────────────────────┐
│  每场信号携带 v1未刷新/v2 refreshed 标记 + last-check    │
│  Δdev 记录 → 周度审计:触发率/refresh率/跨轴未检出率      │
│  → 异常进 ② 队列(verification_status=pending)          │
│  待回测清单最高优先级:贴线抖动场 refresh 阈值 0.10%→     │
│  0.05% + 写后60秒复核(§7, 先回测误伤再落地)             │
└────────────────────────────────────────────────────────┘
```

**监控环指标**（周度手工审计，阶段 3 接 automation）：
- last-check 触发率（Δdev≥0.10% 占比）、refresh 率、refresh 后仍跨轴率
- v1/v2 标记分布（`refresh_state` 字段）
- 贴线抖动场（摆动市+|dev|<0.05%）的信号发出后跨轴率——5pm-et 类问题的检测指标

## 4. 五条护栏（违规即过拟合机器）

1. **学习率控制**：每轮落地最多改 2-3 个格子 / 1 个权重——防止一次重算把表全部洗掉
2. **n<30 永不落规则**：分桶必配 Wilson 95% 下界；四维表当前 17 个非空格全部 n<30，因此只有"合并口径达标"的格子可落（§8 首例：0-2 档合并 n=37）
3. **人工批准永远在落地前**：round24 用户亲自回退封顶 0.60 的先例说明——数据给局部最优，战略判断留人
4. **30 场监控窗可回滚**：触发条件与流程见 §11
5. **概率表折扣 ≠ 风控**：现行架构下 bot 不读 probability/confidence 定价（`hermes_1h_bot.py` "不再读 probability/confidence 做定价"）、金额缩仓已废除（金额按 UI bet_amount 全额）、EV 仅日志——统计层学习只改日志字段。想让学习影响真金白银，须先做产品决策（恢复 confidence→仓位联动），那是独立议题，见 §10

## 5. 数据口径与统计纪律

- 样本口径：快照×已结算匹配、引擎 `extract_factors`+`judge` 复算（与实盘校验层同源）
- 区间估计：**Wilson score 95%**（非 Wald 正态近似——小样本下 Wald 偏窄，43.3% vs 52.5% 的差异即来自公式选择）。示例：37 场 25 胜 → 67.6%，Wilson 区间 [51.5%, 80.4%]；Wald 会给 [52.5%, 82.7%]，小样本不可用 Wald
- 时间切分检查：每格必做前半/后半对比，区分"稀释"（小样本运气被摊平）与"恶化"（近期机制变化）——前者校准即止，后者须查根因
- Wilson 数字必须标明归属格子（n、胜率、格子名），禁止跨格子挪用——43.3% 是摆动市子格（13/20）的下界，不是 37 场合并格（51.5%）的下界

## 6. 候选规则 schema（v1，已冻结；本节是合约摘要）

**权威定义**：`scripts/candidate_schema.json`（JSON Schema draft-07，schema_version=`candidate-patch.v1`）。
**校验/状态机入口**：`scripts/candidate_pipeline.py`（含文件锁、状态迁移、ID 幂等、allowlist 校验）。
**存储**：`data/candidate_patches.json`（顶层 `{schema_version, updated_at_utc, candidates[]}`）。

### 6.1 v1 相对旧版的关键变化

1. **流程状态与证据分离**：`verification_status` 仅承载流程（pending / proposed / accepted / deployed / monitoring / kept / reverted / rejected），证据迁移到 `verification_evidence`（pending / self_verified / engine_verified）。旧记录 `verification_status: self-verified + 状态: proposed` 拆为新两条
2. **field_paths 强制**：`condition.field_paths[]` 必须为精确路径（如 `judge.net`、`extract_factors.order_flow`），禁止模糊字段名（round34.1 教训）
3. **provenance_slugs 强制**：`source.provenance_slugs[]` 必须含触发该候选的所有 slug（不止最后一个），保证审计可重定位（解决"P0 数据 71.6% 不可复现"这类教训）
4. **strategy_version + model_version 必填**：所有候选按版本分段，防止混合版本归因污染
5. **目标文件 allowlist**：`action.target.file ∈ {scripts/rule_engine.py, scripts/signal_validator.py, scripts/hermes_1h_bot.py, scripts/write_signal.py}`；`prompt_exec.md` 与 `prompt.md` **永不允许**

### 6.2 状态机

```
pending → proposed（反事实回测：n≥30 + behavior_changed≥1 + EV>0 + Wilson CI 下界>0）
proposed → accepted（BOSS checklist 全过；scripts/candidate_approve.py CLI）
accepted → deployed（双 selftest 通过 + 部署清单完整）
deployed → monitoring（30 场窗口启动）
monitoring → kept | reverted（自动判定；reverted 走 original_sha256 实际回滚代码 + 双 selftest）
任意 → rejected（BOSS 否决或证据不足）
```

### 6.3 进入 proposed 的必要条件

1. `eligible_sample_count ≥ 30`（快照×已结算可复算样本；n<30 仅告警不落规则）
2. `behavior_changed ≥ 1`（direction/action/EV/cap 任一维度翻转——教训1 的教训：全库仅命中来源场次自身且引擎方向本来就对，行为改变数=0，永不立项）
3. `net_effect > 0`（变体相对基线 EV 差为正）
4. `paired_ev_bootstrap95.lower > 0`（配对 bootstrap 下界为正）

**简化假设**（沿用旧 §6）：门槛用胜率差/配对 EV 差而非成交 P&L 差。在固定 $10 注额、成交价 0.5-0.6 区间下，二元盈亏幅度近似对称；若注额/定价策略变化或进入 P2-3 walk-forward，升级为 P&L 口径（候选回测必须复用 `scripts/fill_bias_backtest.py` 的三宇宙划分：信号宇宙 / taker 可成交宇宙 / 实际成交宇宙，不能只看方向胜率）。

**结构层额外要求**（沿用旧 §6）：提案必须配 ≥3 个跨 regime 反事实场景（不可只拿来源场次），且须核对与既有规则版本的冲突（教训1 与 round20/22/23/31.1 四轮先例正面冲突是典型反例）。

### 6.4 设计稿与盲区

完整设计见 `docs/hermes_candidate_pipeline_plan.md`（plan-v1 锚点）。该管道可减少约 70% 低级过拟合和误落地问题；剩余 30% 来自（a）同一批历史数据被反复查看、（b）多重候选选择偏差、（c）regime 非平稳性——这三条机器规则化机制都解决不了，须 P2-3 时间序列 walk-forward benchmark + 预注册候选集 + 候选外样本验证。

## 7. 5pm-et 反例案例（2026-08-20，时序层 bug 的完整解剖）

**事件**：4pm-et −$9.90 + 5pm-et −$10 连续两亏，两份"教训"直指 G5 缺强翻 UP 规则。

**真相时间线**：
| 时刻 | 事件 | 数据 |
|---|---|---|
| ET :12 | 快照一 | dev=−0.034%，AI 手算 S₀=−7 → DOWN |
| ET :12-13 | last-check | Δ=0.0065% < 0.10%，未跨轴 → 通过（round33.2 铁律正确执行） |
| ET :13 | 写信号 DOWN，引擎校验放行（校验层读与分析同源数据） | |
| **ET :13-15** | **价格跨轴**（锚定 ±0.05% 内随机游走） | dev: −0.034% → +0.045% |
| ET :15 | 快照二：price_position/order_flow/kline 符号全翻，引擎复算 S₀=+4 → **UP**（实际结算 UP，引擎方向是对的） | |
| 结算 | DOWN 单 LOSS −$10 | |

**三个结论**：
1. 病因是**贴线抖动场的快照时差**，不是 G5 缺规则——反事实：教训1（4H≥+700+1H≤−30+|dev|<0.05% 强翻 UP）全库 210 场仅命中本场，且引擎方向本来就是 UP，行为改变数=0，净效果=0
2. **校验层跑 last-check 救不了**：跨轴发生在 :13-:15，校验层即使 :13 实时查价也在锚下，照样放行
3. 有效药方（待回测）：①贴线抖动场（摆动市+|dev|<0.05%）refresh 敏感度 0.10%→0.05% + **写后 60 秒复核**；②承认该类场次接近掷硬币，靠降置信度处理（联动恢复后才有真金白银效果）。**两条都须先回测量化误伤/延迟成本，进监控环待回测清单最高优先级，不进第一轮落地**

**本案例的定位**：所有未来教训的验证参照——任何"教训"进队列前，先问三个问题：引擎口径下这场本来就对吗？行为改变数是多少？净效果是多少？

## 8. 第一轮落表记录：0-2 档顺PM 降级（round35）

**格子**：四维表 |净分|0-2 档 × 非贴线 × 顺PM

**数据依据**（`scripts/regime_split_replay.py`，2026-08-21，210 场全库）：

| 口径 | n | 胜率 | Wilson95 区间 |
|---|---|---|---|
| 原表（round30 时代） | 15 | 93.3% | [70.2%, 98.8%] |
| 本次合并实测 | **37** | **67.6%** | **[51.5%, 80.4%]** |
| ├ 摆动市子格 | 20 | 65.0% | 下界 43.3% |
| ├ 趋势市子格 | 17 | 70.6% | 下界 46.9% |
| 时间切分：前半 | 18 | 83.3% | — |
| 时间切分：后半（8/18 起） | 19 | **52.6%** | 下界 31.7% |

**判断**：
- 原表 93.3% **超出本次 Wilson 上界 80.4%** → 原值被新数据否定
- 时间切分 83.3%→52.6% = **恶化非稀释**（round31+ 时代该档接近随机）
- 拆分格子 n<30 不独立落表（护栏2），只落合并口径
- 恶化的可能机制（待阶段 3 提案验证）：round31 盘感因子族加入后弱信号档被稀释 / 8 月中旬市场 regime 变化 / 原 15 场本身小样本运气——不预判，攒数据

**改动**：`rule_engine._probability` 该格 `93.3,"高"` → `67.6,"低"`。按三档定义（高≥80 | 中 70-80 | 低<70），67.6%<70% 必须落"低"，非"中"。

**影响评估**：
- 实盘行为：**零**（bot 不读 probability/confidence 定价、金额按 UI 全额、EV 仅日志）
- 日志变化：该档 position_scale 默认 1.0→0.5（中/低置信档），仅日志标注不改金额（8/12 决策）
- 该档每场 EV 日志值将下降 ~25.7pp（93.3−0.60×100=33.3 → 67.6−60=7.6），复盘归因时注意口径切换

**回滚触发**（§11）：落表后 30 场内若该档出现引擎方向胜率 <51.5%（本次 Wilson 下界）的持续偏离，回滚至 93.3/高 并标记该格"数据不稳定，冻结至 n≥60"。

## 10. 回溯风险声明：confidence→仓位联动恢复时

本轮 0-2 档降级**仅在"confidence 是纯日志"前提下成立**（bot 不消费、金额不联动、EV 不拦截）。**若未来恢复 confidence→仓位联动（或引入任何"读 probability 定价/仓位"机制），本轮降级将直接影响实盘 P&L，届时必须先跑 P&L 回测**（按成交价×方向×注额重放全部 37 场 + 后续新场次），不可默认降级是永久正确决策。恢复联动 = 触发本声明 = 先回测再上线。

## 11. 回滚机制

- **触发条件**（落表后 30 场监控窗内，任一命中即回滚）：
  - 该格引擎方向胜率持续低于落表值 Wilson 下界（0-2 档：<51.5%）
  - 全量胜率跌破 70%（210 场基线 74.8% 的 Wilson 下界）
  - 用户人工判断（保留最终否决权）
- **回滚操作**：`rule_engine._probability` 恢复旧值 + selftest 断言还原 + 锚点抬升 round35.1（版本只递增不回退）+ SYNC_MAP 全链标注"round35 回滚"+ 该格标记冻结（至 n≥60 或根因查明）
- **责任方**：当前手工（复盘会话周检 drift_alerts.jsonl + 该档胜率）；阶段 3 接 automation 自动告警

## 12. 失败处理

- **selftest 失败 → 中止落地**（SYNC_MAP 铁律，无"带警告落地"选项）：本轮落表若 `rule_engine.py --selftest` 38 断言或 `signal_validator.py --selftest` 6 断言失败（signal_validator case4/5 为历史已知失败，不计），立即 git 还原 `rule_engine.py`，检查四维表断言同步遗漏，修复后重跑
- **校准工具运行失败**（快照损坏/字段缺失）：fail-open 跳过该场（与既有 replay 脚本一致），产出报告标注有效样本数；连续两轮样本数 <150 时人工检查快照归档链路
- **drift_alerts.jsonl 无消费**：周度人工查（当前）；若连续 4 周未消费，阶段 3 提案强制接 automation（防告警变成死数据）
