## 1. 产品定位与商业模式

### 1.1 产品定位

**一句话**：面向 Polymarket/预测市场交易者的"AI 策略自动化交易平台"——用户接入自己的 Polymarket 钱包，软件每小时自动分析 BTC 1H 涨跌并代为挂单，内置严格风控与回测验证。

**目标用户画像**：
- 核心：Polymarket 活跃交易者、加密量化爱好者、DeFi 用户
- 次级：想被动参与预测市场的普通散户（强调"全自动+风控"）
- 不宜定位：专业量化机构（当前策略容量有限）

### 1.2 商业模式（三选一，推荐 A+B 混合）

| 模式 | 形态 | 优点 | 缺点 | 结论 |
|------|------|------|------|------|
| **A. 本地执行 + 云端 SaaS 管控（推荐）** | 客户端软件在用户机器跑交易引擎（私钥不出本机）；云端负责账号/授权/订阅/信号同步/统计 | 私钥安全、合规风险低、部署简单 | 需维护双端 | ⭐ 首选 |
| B. 纯云端托管 | 用户把私钥托管给我们 | 免部署 | **私钥托管=巨坑**，出险即信誉毁灭 | 不推荐 |
| C. 信号订阅 | 只卖每小时信号，用户自己下单 | 轻量 | 价值感弱、难复购、易被搬运 | 可作引流层 |

**推荐路径**：先用 **C（信号订阅）** 验证付费意愿 → 过渡到 **A（本地执行+SaaS）** 作为正式付费产品。

### 1.3 收入结构

- 订阅费（月付/年付/终身）
- 高级策略包（一次性或订阅解锁，如"时段加权包""多市场包"）
- API 接入（机构向，远期）

## 2. 目标系统架构设计

### 2.1 总体架构图（模式 A：本地执行 + 云端管控）

```
┌───────────────────────── 用户侧（本地） ─────────────────────────┐
│                                                                   │
│  ┌──────────────┐   ┌──────────────┐   ┌──────────────────────┐  │
│  │ 采集器 Daemon │   │  执行引擎      │   │ 本地 Web UI (可选)     │  │
│  │ hermes_collect│──▶│ HermesEngine │   │ 只读监控 + 策略开关     │  │
│  │ (打包进产品)   │   │ (重构bot核心) │   └──────────────────────┘  │
│  └──────────────┘   └──────┬───────┘                              │
│          │                 │                                       │
│          │ 行情/市场数据    │ 信号+订单状态                           │
│          ▼                 ▼                                       │
│  ┌────────────────────────────────────────────┐                    │
│  │ 本地分析引擎：RuleEngine(确定性) + Validator │                    │
│  │ (LLM 可选扩展，默认纯规则，零 API 成本)       │                    │
│  └────────────────────────────────────────────┘                    │
│           │ 加密私钥库 (Keychain/加密文件, 永不外发)                 │
│           ▼                                                       │
│      Polymarket API (Gamma/CLOB)                                   │
└─────────────────────────────────────────────────────────────────────┘
                 │ HTTPS (代理隧道/长轮询)
                 ▼
┌───────────────────────── 云端（SaaS 管控层） ──────────────────────┐
│  API Gateway (HTTPS/WSS)                                          │
│  ├─ Auth/User  注册登录、JWT、RBAC                                │
│  ├─ License    激活/心跳/吊销/机器指纹                             │
│  ├─ Billing    订阅、支付 webhook、用量                           │
│  ├─ Sync       信号结果上报、绩效统计、策略包下发                    │
│  └─ Admin      后台管理、用户数据看板                              │
│  数据层：PostgreSQL(主) + Redis(缓存/队列) + S3(日志/快照归档)       │
└─────────────────────────────────────────────────────────────────────┘
```

### 2.2 后端技术选型（云端）

| 组件 | 选型 | 理由 |
|------|------|------|
| API 框架 | **FastAPI**（Python） | 与现有 Python 代码零语言断层，自动 OpenAPI 文档，async + WebSocket 原生支持 |
| 前端 | **Vue 3 + TypeScript + Vite**（或 React + AntD） | 前后端分离；组件生态成熟；现有 dashboard 的 JS 逻辑可迁移 |
| 主数据库 | **PostgreSQL 16** | 事务、JSONB（策略配置/信号快照）、窗口函数（绩效统计）、成熟可靠 |
| 缓存/队列 | **Redis** + Celery | 实时状态推送、任务队列（回测任务）、限流 |
| 实时通信 | **WebSocket**（WSS） | 本地端 ↔ 云端状态同步、告警推送 |
| 对象存储 | S3 兼容（腾讯云 COS/MinIO） | 回测数据包、日志归档 |
| 鉴权 | JWT + OAuth2（Google/微信 登录可选） | 标准方案 |
| 支付 | **Stripe / LemonSqueezy**（国际）；国内备选 微信/支付宝聚合 | 订阅管理 + webhook |
| 部署 | Docker + Docker Compose（单机起步）→ K8s（放量后） | 渐进 |
| 反向代理 | Nginx / Caddy（自动 HTTPS） | 标准 |

**数据库选型对比**（供决策）：

| 方案 | 优点 | 缺点 | 适用 |
|------|------|------|------|
| PostgreSQL ⭐ | 事务/JSONB/窗口函数/生态全 | 需运维 | **云端主库（首选）** |
| SQLite | 零运维、嵌入式 | 并发写弱、无网络 | **本地端缓存/回测临时库** |
| ClickHouse/DuckDB | 列存、回测/时序极快 | 运维重/能力单一 | **回测大数算**（可选，DuckDB 嵌本地） |
| MongoDB | 灵活 | 事务弱、性能不及 PG | 不推荐 |

**决策**：云端统一 **PostgreSQL**（一个库管用户/订阅/授权/信号/绩效）；本地端 **SQLite** 存回测与缓存；时序分析用 PostgreSQL 分区表 + 可选 DuckDB。

### 2.3 本地执行端技术选型

| 组件 | 选型 | 理由 |
|------|------|------|
| 运行时 | Python 3.11+ 打包为独立应用 | 复用全部现有代码 |
| 打包 | **PyInstaller**（Windows/macOS）+ 代码签名（Apple notarization / 微软 EV 签名） | 一键安装体验；签名同时解决"被杀毒误报" |
| 进程管理 | 内置 Daemon（Supervisor 或自写 service） | 替代 launchd，跨平台 |
| 私钥存储 | **Keychain (macOS) / Credential Manager (Win) / 加密文件(AES-GCM)** | 私钥永不明文落盘 |
| 本地存储 | SQLite + 加密 | 缓存、回测 |
| 自动更新 | 自研更新器（签名 manifest + 差分包 + 回滚） | 见 §6 |

### 2.4 信号管道重构（关键迁移）

现状：`/tmp/hermes_signal.jsonl` 文件队列 + 进程轮询 → 产品化后：

```
Collector ──▶ 本地信号总线（内存队列 + SQLite 持久化）
                 │
                 ▼
            RuleEngine 分析 ──▶ Validator 校验 ──▶ ExecutionEngine 下单
                 │                                  │
                 ▼                                  ▼
            绩效事件流 ─────────────────────────▶ 云端 Sync (批量上报)
```

**原则**：本地端**全离线可跑**（规则引擎确定性分析，零 LLM 成本）；云端只是管理/统计/授权层。LLM 分析作为"高级策略包"可选开启（走云端代理，按调用计费）。

### 4.2 权限分级（RBAC）

| 角色 | 权限 | 对应订阅 |
|------|------|---------|
| `guest` | 浏览产品页、回测 demo | 未登录 |
| `free` | 限频信号预览、5 次回测 | 免费注册 |
| `basic` | 单策略实盘（本地执行）、基础风控、基础告警 | Basic 订阅 |

**权限校验**：后端 RBAC 中间件（FastAPI dependency），前端按角色渲染。

### 4.3 订阅与付费

- 支付渠道：**Stripe**（信用卡/PayPal，国际用户）优先；上架 **Gumroad / LemonSqueezy** 走"Sales Tax/增值税合规"；国内用户备选 支付宝当面付（走独立商户）。
- 订阅状态机：`trialing → active → past_due → canceled → expired`；webhook 驱动。
- 权益即时生效：支付成功 → 授权服务器签发/续期 license token → 本地端同步。
- 取消流程：可自助取消，到期前 7 天邮件提醒；数据保留 90 天后匿名化。
- 退款政策：7 天无条件（防纠纷，信用卡拒付率控制）。

## 5. 许可证与反盗版机制

### 5.1 授权模型（推荐：离线激活 + 在线心跳混合）

```
┌──────────┐  激活请求(机器指纹+licKey)   ┌──────────┐
│ 本地端    │ ────────────────────────────▶ │ 授权服务器 │
│          │ ◀──────────────────────────── │ (RSA 私钥) │
│          │   签发签名许可证 (JWT/自定义)    └──────────┘
└──────────┘
  · 许可证含：用户ID、订阅等级、到期时间、机器指纹哈希、签发时间
  · RSA-2048 签名校验（公钥内嵌本地端，私钥仅存云端）
  · 心跳：每 24h 一次（允许离线宽限期 72h，超期降级为只读模式）
```

### 5.2 具体机制清单

| 机制 | 实现 |
|------|------|
| 机器指纹 | 收集 CPU 序列号/主板 UUID/磁盘序列号/MAC（哈希拼接 + HMAC），不上传明文 |
| 许可证文件 | 签名后写入本地 `~/.hermes-license`（权限 0600），防篡改 |
| 时间防回拨 | 心跳记录"云端时间锚点"，本地时间早于锚点-宽限 → 判定回拨，要求重新激活 |
| 多设备限制 | 免费/Basic 限 1 设备，Pro 限 2；超额提示在旧设备吊销 |
| 吊销 | 管理员后台一键吊销（拉黑 licKey + 指纹），客户端心跳时生效 |
| 防调试 | 核心校验逻辑做混淆（PyArmor / Nuitka 编译打包） |
| 水印 | 许可证含 user_id，日志/错误上报带水印，泄露可溯源 |
| 云端 API 鉴权 | 本地端所有云端 API 带 license token，与用户 token 绑定 |

### 5.3 反盗版边界（务实声明）

- **不存在绝对防破解**：目标是把破解成本提高到 > 购买成本。
- 核心防御是**云端依赖**：信号/策略包/回测数据/LLM 增强走云端，纯本地破解只能拿到"无更新的旧版本"。
- 法律侧：用户协议 + EULA + 软件著作权登记（产品稳定后登记软著，1-2 个月可下证）。

## 6. 部署与自动更新方案

### 6.1 本地端打包

| 平台 | 方案 |
|------|------|
| macOS | PyInstaller onefile/dmg + `codesign` + Apple notarization（防 Gatekeeper 拦截） |
| Windows | PyInstaller + Inno Setup 安装器 + EV 代码签名（微软 SmartScreen） |
| 更新通道 | 自研 updater：下载 `manifest.json`（版本/校验和/签名）→ 差分或整包 → 校验 → 替换 → 回滚（保留上一版） |
| 升级灰度 | 云端按用户比例灰度新版本，出问题可远程锁定版本 |

### 6.2 云端部署

```
VPS (起步 2C4G) ── Docker Compose：
  ├─ api (FastAPI, 多 worker)
  ├─ worker (Celery: 回测/信号推送/统计)
  ├─ pg (PostgreSQL 16)
  ├─ redis
  └─ caddy (自动 HTTPS)
放量后：加负载均衡 → 托管 PG → K8s
```

- 备份：PG 每日 pg_dump 到对象存储 + 保留 30 天；灾备演练。
- 监控：云端自身 uptime 探针 + 告警（云端挂 ≠ 本地交易停，本地离线自治是设计特性，需向用户明示）。

### 6.3 数据与密钥安全

- 用户私钥**永远只在本地**，云端不接触、不上传。
- 本地私钥加密存储（Keychain/凭据管理器/AES-GCM 文件）。
- HTTPS/WSS 全链路 + 证书固定（防中间人，可选）。
- 审计日志：所有下单/授权变更/登录记录留痕（云端）。
