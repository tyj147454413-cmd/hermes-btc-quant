## 一、当前系统定位

### 1.1 系统定性

Hermes 当前属于：

> **规则驱动的系统化自动交易系统（Rule-based Systematic Trading），是量化交易的早期形态，但还不是完整的量化交易系统。**

### 1.2 已具备的能力

| 模块 | 现状 | 成熟度 |
|---|---:|---:|
| 策略规则化 | 11 步分析流程 + H1-H12 硬约束 + G1-G6 门槛层 | 较高 |
| 信号确定性复算 | `rule_engine.py` + `signal_validator.py` | 较高 |
| 自动采集与落盘 | `hermes_collect.py` + `data/snapshots/` | 中等 |
| 自动信号写入 | `write_signal.py` | 较高 |
| 自动执行 | `hermes_1h_bot.py` 按信号挂单 | 中等 |
| 复盘闭环 | 复盘 → 报告 → Obsidian 笔记 | 中等 |
| 历史统计 | 场景重放、反事实回测、胜率分桶 | 初级 |
| 风险控制 | 信号级风控 + bot 层 PM 硬拦截 | 初级 |

### 1.3 当前最主要问题

1. 大量阈值来自人工复盘，缺少统计显著性和过拟合检验。
2. 回测不是完整事件驱动回测，未完全计入滑点、手续费、未成交机会成本。
3. 数据以 JSON 快照为主，缺少结构化特征存储和完整盘口历史。
4. 执行层只有“挂一个限价单”，缺少挂价优化、撤单重挂、未成交处理。
5. 风控是信号级，不是组合级；没有日亏损熔断、回撤熔断、策略漂移熔断。
6. 绩效归因粗糙，缺少 Sharpe、Sortino、最大回撤、成交率、执行成本等标准指标。
7. `position_scale` 目前仅日志标注，不实际影响下单金额。
8. `bet_amount` 依赖 UI，曾出现 `$0.50 / $5.0` 不稳定问题。

## 二、与真正量化交易的差距

### 2.1 差距总览

| 模块 | 当前得分 | 真正量化 | 差距 |
|---|---:|---:|---|
| 策略规则化 | 7 | 10 | 小 |
| 回测研究 | 3 | 10 | 大 |
| 数据基础设施 | 3 | 10 | 大 |
| 执行与订单管理 | 2 | 10 | 大 |
| 风险管理 | 2 | 10 | 大 |
| 绩效归因与监控 | 2 | 10 | 大 |
| 工程化与可复现 | 3 | 10 | 大 |

综合：约 **3/10**。方向正确，但基础设施和研究体系尚未建立。

### 2.2 差距详解

#### 2.2.1 策略研究层

- 规则多来自人工复盘和单场教训，阈值如 `0.05% / 0.15% / 0.23 / 0.60 / 2.33 / 0.43 / 3:1 / 5:1 / 30 / 50 / 90 / 70%` 多数未做敏感性分析。
- 回测样本量小：88 场、92 场、120 场、239 场等，统计功效不足。
- 缺少事件驱动回测器、Walk-forward 滚动验证、多重检验校正、基准策略对照。

#### 2.2.2 数据层

- 已有快照归档，但缺少：
  - 完整盘口历史档位。
  - Tick/微观价格。
  - 结构化特征存储（Parquet/Feature Store）。
  - 数据质量门禁和自动告警。
  - 跨市场数据：BTC 现货、CME、永续、资金费率历史等。

#### 2.2.3 执行层

- 只有固定 `max_price=0.60` 限价单。
- 无挂价优化、追价策略、撤单重挂、部分成交处理。
- 无订单生命周期管理。
- 无交易成本分析。

#### 2.2.4 风控层

- 已有 G1-G6、H12、H13、9.7、bot PM <0.25 硬拦截。
- 缺少：
  - 日/周止损线。
  - 波动率目标仓位。
  - 最大回撤熔断。
  - 策略漂移自动降级。
  - 保证金/资金使用率控制。

#### 2.2.5 绩效归因与监控

- 已有 done.jsonl、复盘笔记、`strategy_version` 分段。
- 缺少：
  - 标准绩效指标：Sharpe、Sortino、最大回撤、Calmar、盈亏比、期望值、成交率、胜率置信区间。
  - 归因拆分：方向 alpha、执行 alpha、费用、滑点、时机贡献。
  - 实时监控面板和自动告警。
  - 模型再训练/再校准流程。

## 三、总体目标

### 3.1 总目标

在 **6-8 个月** 内，将 Hermes 从“规则驱动的自动交易工具”升级为“数据驱动、可研究、可验证、可风控、可监控”的完整量化交易系统。

### 3.2 分阶段目标

| 阶段 | 时间 | 目标 |
|---|---|---:|---|
| 阶段 0 | 1-2 周 | 止血和固化：稳定现有链路，修复金额、版本、监控问题 |
| 阶段 1 | 2-4 周 | 建立事件驱动回测框架和阈值敏感性分析 |
| 阶段 2 | 3-6 周 | 数据与特征升级：盘口、成交、跨市场、结构化存储 |
| 阶段 3 | 4-8 周 | 模型层升级：规则为 Baseline，引入 ML 概率模型和 Meta-Labeling |
| 阶段 4 | 2-4 周 | 执行层升级：动态挂价、未成交处理、订单审计 |
| 阶段 5 | 2-4 周 | 组合级风控：止损熔断、波动率目标、漂移监控 |
| 阶段 6 | 长期 | 监控与迭代：仪表盘、自动报告、再训练、A/B 测试 |

## 阶段 0：止血和固化（1-2 周）

### 目标

先让现有系统稳定、可复现，不再出现文档漂移、金额异常、信号漏单等事故。

### 任务 0.1：修复 bet_amount 和 position_scale

**问题**

- `position_scale` 只写日志，不实际影响金额。
- `bet_amount` 依赖 UI，曾出现 `$0.50 / $5.0` 抖动。

**工作内容**

1. 在 `hermes_config.json` 中新增：
   ```json
   {
     "risk": {
       "default_bet_amount": 5.0,
       "min_bet_amount": 3.0,
       "max_bet_amount": 20.0,
       "risk_per_trade_pct": 0.5
     },
     "position_scale_enabled": true
   }
   ```
2. 修改 `hermes_1h_bot.py`：
   - 优先从信号 `position_scale` 读取仓位比例。
   - 如果 `position_scale` 存在且为 `0.5`，下单金额 = `default_bet_amount × 0.5`。
   - 如果 `position_scale_enabled=false`，保持日志模式。
3. 修复 UI bet_amount 读取抖动：
   - 增加金额合法性和稳定性检查。
   - 若 UI 金额 < min_bet_amount，使用配置默认值。
4. 在 `write_signal.py` 中增加 `bet_amount_override` 字段校验。

**产出**

- 金额不再依赖 UI，`position_scale` 可以真实缩仓。
- 配置文件和文档同步更新。

**验收标准**

- 连续 3 天无 `$0.50` 异常金额。
- `position_scale=0.5` 时 bot 实际下单金额为默认金额的 50%。

### 任务 0.2：规则与版本一致性固化

**问题**

- 规则、SKILL、引擎版本曾出现漂移。
- SKILL 内嵌表和 `prompt_exec.md` 曾出现 G3 两种相反口径。

**工作内容**

1. 在 `SKILL.md` 增加机器可读字段：

2. 在 `write_signal.py` 或 `signal_validator.py` 中增加启动时锚点比对：
   - 读 `prompt_exec.md` 顶部锚点。
   - 读 `rule_engine.py` 的 `RULE_VERSION`。
   - 不一致时写 risk 并打印警告。
3. 建立版本一致性 CI：
   - `python3 scripts/rule_engine.py --selftest` 必须通过。
   - `python3 scripts/signal_validator.py --selftest` 必须通过。
   - 新增 `scripts/check_rule_anchor.sh`，检查 `prompt_exec.md` / `prompt.md` / `rule_engine.py` / `SKILL.md` 锚点一致。
4. 每周自动跑一次全量版本一致性检查。

**产出**

- `rule_version` 字段。
- 版本一致性检查脚本。
- 所有文档锚点统一。

**验收标准**

- 任何一处改版未同步时，`check_rule_anchor.sh` 能自动发现并告警。

### 任务 1.3：阈值敏感性分析

**工作内容**

1. 对以下阈值做网格扫描：
   - 贴线阈值 `0.05% / 0.10%`。

2. 做执行质量归因。

**产出**

- `data/order_audit.jsonl`。

**验收标准**

## 阶段 5：组合级风控（2-4 周）

### 目标

让系统能“活得久”，而不是只看单场对错。

### 任务 5.1：固定风险金额

**工作内容**

1. 每单风险 = 总资金 × 0.5%-1%。
2. 不因为连续盈利就突然加仓。

**产出**

- 风险金额计算模块。

**验收标准**

- 单笔亏损不超过预设比例。

---

### 任务 5.2：日亏损熔断

**工作内容**

1. 单日亏损超过 X% → 停止交易。
2. 连续亏损 N 场 → 降低仓位或暂停。

**产出**

- `scripts/risk_manager.py`。

**验收标准**

- 触发熔断后系统自动停止。

---

### 任务 5.3：波动率目标仓位

**工作内容**

1. 波动率 >0.5% 时仓位减半。
2. 波动率 <0.1% 时可适当提高，但设上限。

**产出**

- 波动率目标仓位模块。

**验收标准**

- 仓位随波动率自动调整。

---

### 任务 5.4：策略漂移监控

**工作内容**

1. 滚动 30 场胜率。
2. 滚动 EV。
3. Wilson95 下界。
4. 跌破保本线自动暂停。

**产出**

- `scripts/drift_monitor.py`。

**验收标准**

- 策略失效时能自动暂停。

## 六、关键指标定义

| 指标 | 公式/口径 | 用途 |
|---|---|---:|---|
| 胜率 | 方向正确次数 / 已结算单数 | 基础 |
| EV | `P(win) − max_price×100`，百分数 | 期望收益 |
| 成交率 | 实际成交单 / 信号单 | 执行效率 |
| Sharpe | `(年化收益 − 无风险利率) / 年化波动率` | 风险调整收益 |
| Sortino | 下行波动率版 Sharpe | 只看下行风险 |
| 最大回撤 | 权益曲线最大峰谷跌幅 | 风险 |
| Calmar | 年化收益 / 最大回撤 | 回撤调整收益 |
| 盈亏比 | 平均盈利 / 平均亏损 | 收益结构 |
| Wilson95 下界 | 胜率置信区间下界 | 统计显著性 |
| 执行成本 | 信号价 − 实际成交价 | 执行质量 |

## 七、风险与依赖

| 风险 | 影响 | 应对 |
|---|---|---:|
| 回测过拟合 | 新规则上线即失效 | Walk-forward + 阈值敏感性 + 样本外验证 |
| 数据质量差 | 回测和实盘结论失真 | 数据质量门禁 + 自动告警 |
| 执行滑点大 | 实际成交远差于信号 | 订单审计 + 动态挂价 |
| 单策略失效 | 连续亏损 | 漂移监控 + 日亏损熔断 |
| 文档/代码漂移 | 规则执行不一致 | 版本一致性 CI |
| 金额不稳定 | 仓位错误 | 配置化 bet_amount + 校验 |
